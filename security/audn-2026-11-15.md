## #24：同一個 skill 檔案的 metadata 編輯路徑

受認證保護的 `PUT /api/skills/{name}/meta` 經 `fsUpdateSkillMeta` 讀取已安裝的 `SKILL.md`，再交給 [`rewriteSkillFrontmatter`](../server/server_mgmt.go)。基準版本先執行 `strings.Split(string(content), "\n")`，因此上傳 parser 的修補不會保護這個後續呼叫。有效檔案的 body、frontmatter 中大量空行，以及尚未通過格式驗證的檔案，都會先產生逐行配置。許多很短的非空欄位還會擴張 `[]kv`。

修補先用 byte slice 找出 frontmatter／body 邊界，格式不完整時立即回傳；第二次掃描直接輸出欄位，只以固定三個旗標記錄可更新字串欄位的首次出現位置，最後附上原始 body。沒有逐行 string 或 key/value 容器。這保護的是**已登入管理者處理不可信 skill 內容時的資源邊界**；本次沒有以服務 OOM 或匿名 DoS 作為驗證結果。

### 有界的修補前後量測

[`server/skill_metadata_security_test.go`](../server/skill_metadata_security_test.go)以 `testing.Benchmark(...).AllocedBytesPerOp()` 呼叫實際 helper，使用約 64 KiB 合成資料。以下為 Go 1.26.3／linux amd64 的本機結果；數字是每次呼叫配置的 bytes，**不是程序峰值 RSS**。測試門檻為 `4 × input bytes + 8 KiB`，保留輸出與 buffer 成長空間。

| 輸入 | Input bytes | 基準版本 bytes/op | 修補後 bytes/op | 測試上限 bytes/op |
|---|---:|---:|---:|---:|
| body 大量換行 | 65,570 | 1,352,080 | 73,728 | 270,472 |
| frontmatter 大量空行 | 65,570 | 1,130,917 | 73,728 | 270,472 |
| 重複短欄位 `a:` | 65,569 | 4,522,165 | 221,184 | 270,468 |
| 重複空 key `:` | 65,570 | 6,204,472 | 73,728 | 270,472 |
| 無效開頭 | 65,552 | 1,130,512 | 16 | 270,400 |
| 未關閉 frontmatter | 65,559 | 1,130,513 | 16 | 270,428 |

六個配置量案例在未修改的基準 helper 全部失敗，修補後全部通過；測試斷言未因修補而放寬。九個序列化控制案例則在修補前後皆通過，涵蓋未知欄位順序、重複欄位只改第一筆、nil／空值語意、刪除全部舊 `mcps` 後清理並重附、空 key、非 key 原始文字、CRLF、body 尾端換行與 closing delimiter 位於 EOF。

另使用既有 `buildZip`／`uploadZip` fixture，先呼叫真正的 ZIP 上傳 handler，再呼叫 metadata handler，讀回檔案比對完整結果，確認可壓縮的大量換行 body 與混合換行原樣保留。這是直接 handler 測試，不冒稱已跑完整登入與部署流程。

## #33／#37：資產規則、hostname 正規化與寫入邊界

基準版本能辨識 `127.1`、整數、八進位／十六進位 IPv4，以及 ASCII domain 大小寫與尾端點，但尚未將 `127。0。0。1`、`１２７.０.０.１`、`internal.example。` 等寫法與實際 HTTP transport 的正規化對齊。這會影響 [`assetInterceptHosts`／`matchOne`](../db/asset_intercept_match.go) 所共用的**資產寫入前攔截與儲存後 intent 政策檢查**。

本次使用既有 `golang.org/x/net/idna` 的 lookup profile，只有轉換成功才建立等價關係，再進行數字 IP、CIDR 與 exact-domain 比對。原始 fuzzy-domain、fuzzy-URL、exact-URL 與 fuzzy-IP 候選仍保留；不做 DNS 查詢、不把 exact-domain 擴成子網域 suffix 規則，也不將 IDNA 回傳的「部分結果加 error」視為另一個 hostname 的允許依據。一般國際化網域、數字前綴但仍為網域的名稱、合法 IPv4／IPv6，以及明確設定的非 IDNA 字面名稱均有控制案例。

### 重複尾端分隔符：工具寫入前的拒絕條件

另確認基準版本已有一個原始輸入／儲存形態不一致：`internal.example..` 在寫入前不命中 `internal.example` 的 exact-domain 封鎖；`DomainKey` 去掉一個尾端點後儲存成 `internal.example.`，儲存後比對再去掉一個尾端點才會命中。域名 Upsert 本身沒有先驗證這類原始名稱，因此政策可在寫入前後改變。這與 #33／#37 屬同一類資產政策問題，不另列為第三類漏洞或新 CVE，也不表示後續 intent 檢查已遭繞過。

[`agent/tools_insert.go`](../agent/tools_insert.go)的 `evaluateAssetInputGate` 現在於 `insert_assets` 工具的任何 Upsert 或寫入副作用前，檢查 `Domain`、`BoundDomains` 及可解析 URL 的 hostname。trim 後能由 `netip.ParseAddr` 解析的 IP 位址略過 DNS 尾端分隔符檢查，仍交給正常 IP／CIDR 政策；其餘名稱先依既有儲存行為轉小寫，成功時採用 IDNA lookup 結果，再於**尚未移除任何 root separator** 的形態計算尾端分隔符。兩個以上的 `.。．｡` 會被拒絕。IDNA 失敗時使用映射前的名稱，不採用部分映射結果。這也涵蓋 `internal.example.\u200b.`／`.\u00ad.`：U+200B／U+00AD 經成功 IDNA 映射忽略後，仍須辨識出重複尾點。

此檢查只新增於 **`insert_assets` 工具寫入邊界**，未改動全域 `DomainKey`、既有儲存 key 或所有直接 `AssetStore` 寫入，也沒有加入 URL scheme 限制或全面 malformed-domain 驗證。共用 matcher 對無效輸入的字面規則測試維持原樣，避免讓非法輸入因正規化而取得另一個名稱的允許規則。

三個回歸測試為 `TestSecurityInsertAssetRejectsStoredRootSeparatorMismatch`、`TestSecurityInsertAssetRejectsRepeatedRootSeparators` 與 `TestSecurityInsertAssetGateKeepsValidCandidates`。先確認測試在基準版本因原始／儲存不一致而失敗；僅檢查原始尾點的候選也先被 U+200B／U+00AD 案例否定，再修正映射後的檢查。負向案例涵蓋 domain、HTTP service／HTTPS endpoint URL、非 HTTP service 的 Domain、IP 的 BoundDomains，以及明確允許非法輸入的規則；單一 `.。．｡`、忽略字元後仍只有一個尾點、Unicode／底線名稱、不同子網域、IPv6 URL 與既有 block／allow 行為均保留正常控制。

另以 `TestSecurityInsertAssetScopedIPv6KeepsIPRules` 先重現並修正正常輸入的回歸：`http://[fe80::1%25test..]/` 的 `test..` 是合法 IPv6 zone，不是 DNS root separator。測試使用實際 `url.Parse`／`netip.ParseAddr`，確認沒有規則時可接受，`exact_ip = fe80::1` 與 `cidr = fe80::/10` 的封鎖／允許仍按原政策生效；不因略過 DNS 尾點檢查而略過資產規則。

### 獨立複查發現的 U+0130 回歸

初版 IDNA 候選先轉換再處理既有 Go 儲存大小寫，曾新增一個回歸：`İnternal.example`（U+0130）在候選比對時與 `internal.example` 不同，但 [`DomainKey`](../db/nkey.go) 與 [`normalizeURL`](../db/assets.go) 的既有儲存路徑會先轉成小寫，實際寫入 `internal.example`。這可能讓寫入前檢查通過、儲存後才被拒絕。

此回歸在候選審查中以實際 `DomainKey`、`normalizeURL`／`parseURL` 與 agent insertion candidate 重現，先確認新增案例失敗，再將共用 helper 調整為**先遵循既有儲存的 `strings.ToLower`，再採用成功的 IDNA 結果，最後處理單一 root separator**。原始／儲存候選、原始／正規化規則，以及 block／allow 方向均納入測試。這是修補過程中發現並修正的回歸，不列為原始 `main` 已存在的新增漏洞，也不把寫入前政策缺口說成已繞過後續 intent 檢查。

### 不連網的 transport 證據

[`TestSecurityAssetIDNAUsesActualHTTPDestination`](../db/asset_gate_security_test.go)使用真正的 `http.Transport`，但將 `DialContext` 換成只記錄目的地後立即回傳合成錯誤的 stub。測試確認 Unicode 點號／全形數字進入 `127.0.0.1:80`，以及 IDN 進入對應 ASCII hostname，隨後比對資產規則結果。**沒有建立 socket、解析 DNS 或存取內網服務。**因此可證實的是政策正規化缺口及 transport 的目的地轉換，不是已完成的自動 SSRF。
