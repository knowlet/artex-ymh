# RFC: Harness-leak auditing and authorized exercise traceability

**Status:** Proposed; documentation only  
**Date:** 2026-11-28

## Background and verification

Wiz Research's November 25, 2026 report documents internal intent identifiers appearing in target-side telemetry in real incidents involving agentic offensive frameworks. The report explains why a numeric identifier is a corroborating signal rather than a unique operator identity.

A read-only inspection of artex-ymh's main branch found that intent identifiers remain present in worker context. This confirms a structural risk consistent with the report, not runtime reproduction in this fork. The inspected worker file had Git blob SHA `0d3389d0b4768d9584351d5b8c4346646a60d0eb`. The current fork's database sequence behavior and deployed runtime have not been independently verified in this review.

## Proposed safeguards

Treat intent-related information as an exercise audit signal, not an authorization credential. Restrict exercise execution to explicitly approved assets and time windows. Require independently enforced authorization at the execution boundary, including for tool calls generated by a model; missing or ambiguous scope must fail closed. Record denied operations as well as permitted ones.

Preserve existing audit evidence and defender-visible telemetry. The proposed work must not rewrite, suppress, disguise, or delete identifiers in order to make activity harder to detect or correlate. Provide the authorized exercise owner with an auditable mapping between the exercise authorization, task, intent, tool invocation, timestamp, target, approval decision, and outcome. Keep access to sensitive audit records role-based and retention governed by the exercise agreement. Avoid collecting credentials or unnecessary payloads in those records.

## Defensive validation plan

Use an isolated, owner-controlled test fixture with a local mock service and synthetic data. Do not use third-party systems or production targets for reproduction.

- Run an authorized exercise and verify that a permitted operation and its audit event can be correlated end to end.
- Verify that an operation outside the approved scope is denied before execution and that its denial remains auditable.
- Verify that an operation without an authorization record is denied.
- Verify that model-generated output cannot bypass scope enforcement or alter the audit trail.
- Verify that synthetic intent markers visible in fixture logs remain available to the SOC, and that investigation can distinguish authorized exercises from suspicious activity using the exercise registry.
- Evaluate false positives with unrelated numeric identifiers. Require corroborating context before linking incidents; do not equate a numeric counter with attack count or operator identity.

## Acceptance criteria for a future implementation

1. Authorization and scope enforcement have integration tests using synthetic fixtures.
2. Allowed and denied invocations are traceable to an exercise record.
3. Audit evidence is retained, access-controlled, and protected against unauthorized mutation.
4. Defensive telemetry is preserved and a blue-team reviewer can validate correlation in the fixture.
5. Any implementation PR includes test results and a separate review of authorization, audit integrity, and data handling.

## Non-goals

No changes to identifier allocation, model prompts, naming behavior, network identity, or target-side telemetry intended to reduce detection or attribution. No runtime code, migrations, or deployment changes are included in this RFC.
